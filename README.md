## 시작하기

```bash
cd frontend
npm install
npm run dev
```

`http://localhost:5173` 이 열립니다. **이대로도 그냥 돌아갑니다** — 백엔드 없이
브라우저 안에서만 도는 mock 모드입니다. 화면 작업만 할 거라면 이걸로 충분합니다.

### 실제 백엔드에 붙여서 개발하기

```bash
cd frontend
echo "VITE_API_BASE_URL=https://rise-server-production.up.railway.app" > .env.local
npm run dev
```

배포된 백엔드에 그대로 붙습니다. 별도 서버를 띄울 필요가 없습니다.
`.env.local`은 git에 올라가지 않으니 각자 만들어 쓰세요.

> **주의**: 배포된 백엔드는 실제 DB를 씁니다. 여기서 만든 계정과 그룹은 다른 팀원에게도 보입니다.
> 마음껏 부수면서 실험하려면 백엔드를 로컬로 띄우세요 (`RISE-server` README의 "빠르게 실행하기").

`VITE_API_BASE_URL`을 지우면 다시 mock 모드가 됩니다. 백엔드 없이도 데모할 수 있도록
일부러 분리해 둔 구조이니, **연동한다고 mock 코드를 지우지 마세요.**

## 구조

```
frontend/src
  ├── api/          서버 통신. mock ↔ 실제 백엔드 전환도 여기서 일어남
  │   ├── client.js       ★ 공통 fetch 래퍼, 토큰 처리, 이미지 주소 변환
  │   ├── authApi.js      로그인 / 회원가입
  │   ├── groupApi.js     그룹 생성·참여·설정·나가기
  │   ├── missionApi.js   미션 조회·인증, 시간대별 잠금 해제
  │   ├── mealApi.js      식단 사진 업로드 / AI 분석
  │   └── profileApi.js   내 정보, 캐릭터, 온보딩
  ├── context/
  │   └── AppContext.jsx  ★ 앱 전체 상태(useReducer) + 서버 동기화
  ├── pages/        화면 단위 컴포넌트
  ├── components/   재사용 UI (캐릭터, 미션 카드, 결과 시트 등)
  └── utils/        이미지 리사이즈 등
```

★ 표시한 두 파일이 핵심입니다. 고치기 전에 먼저 읽으세요.

### `client.js` — 모든 통신이 지나가는 곳

- `isBackendEnabled` : `VITE_API_BASE_URL` 설정 여부. 각 API 파일이 이 값으로 mock/실서버를 가름
- `api.get/post/patch/delete/postForm` : 서버 응답 `{ success, data, error }` 껍데기를 벗겨 `data`만 돌려줌
- `fileUrl(path)` : 서버가 주는 `/api/files/{id}` 같은 상대 경로를 완전한 주소로 바꿈.
  **이걸 안 거치면 이미지가 프론트 서버를 찾아가서 깨집니다.**

### `AppContext.jsx` — 상태와 동기화

- `useReducer` 기반. 화면은 `useAppState()` / `useAppDispatch()`로 접근
- `sync()` 가 **15초마다** 서버에서 내 정보·캐릭터·그룹·미션·식단을 다시 받아옴
- 상태는 localStorage에 자동 저장되어 새로고침해도 남음

## 고칠 때 꼭 알아야 할 것

### 1. 서버에 남아야 하는 값은 반드시 API를 호출하세요

가장 많이 낸 실수입니다. `dispatch`만 하면 **내 화면에서만 잠깐 바뀌었다가,
15초 뒤 `sync()`가 서버 값을 도로 가져와 원래대로 돌아갑니다.**

```js
// ✗ 이렇게 하면 그룹을 나간 것처럼 보였다가 다시 들어와집니다
function handleLeaveGroup() {
  dispatch({ type: 'LEAVE_GROUP' });
  navigate('/my');
}

// ✓ 서버에도 알려야 진짜로 나가집니다
function handleLeaveGroup() {
  leaveGroup()
    .catch(() => {})
    .finally(() => {
      dispatch({ type: 'LEAVE_GROUP' });
      navigate('/my');
    });
}
```

실제로 **그룹 나가기, 방 이름 변경, 미션 시작 시간 변경** 세 가지가 이 문제였습니다.
상태를 바꾸는 화면을 만들면 `dispatch` 옆에 API 호출이 있는지 확인하세요.

### 2. 서버가 "없다"고 하면 로컬도 지워야 합니다

`sync()`가 그룹 조회에 실패했을 때 **아무것도 안 하고 넘어가면**, 서버에서는 이미 나갔는데
화면에는 그룹이 계속 보이는 유령 상태가 됩니다. 그 안의 기능은 전부 403이 나면서
아무 반응이 없는 것처럼 보입니다.

단, **403(서버의 확답)과 네트워크 오류를 구분해야 합니다.** 잠깐 끊겼다고 그룹을 지우면 안 됩니다.
`client.js`가 던지는 오류에 `status`와 `code`를 실어 보내니 그걸로 판단하세요.

### 3. 반대로, 서버에 있는 값은 `sync()`가 받아와야 합니다

식단 인증이 **새로고침하면 사라지는** 문제가 있었습니다. `sync()`가 미션·그룹·코인은
받아오는데 식단만 빠져 있었기 때문입니다. 새 데이터를 서버에 저장하기 시작했다면
`AppContext.jsx`의 `sync()`에도 조회를 추가하세요.

### 4. 미션은 서버가 만듭니다 — 로컬에서 만들지 마세요

`generateDailyMissions()`는 **백엔드 없이 데모할 때만** 쓰는 mock 생성기입니다.
백엔드 모드에서 이걸 호출해 화면에 넣으면, 잠깐 보였다가 `sync()`가 서버 세트로 갈아끼우면서
**미션이 저절로 바뀐 것처럼 보입니다.** 그 사이 다른 그룹원에게는 서버 세트가 보이므로
같은 사람의 오늘 미션이 서로 다르게 표시됩니다.

리듀서에서는 `newMissionSet()`을 쓰세요. 백엔드 모드면 빈 배열을 주고 서버가 채우게 합니다.
미션이 바뀌는 시점은 **날짜가 바뀔 때뿐**이어야 합니다.

### 5. 그룹 설정은 서버 값으로 계속 맞춰야 합니다

방 이름·미션 시작 시간처럼 **그룹원 전체가 공유하는 값**은 참여할 때 한 번 받고 끝내면 안 됩니다.

방을 만들 때는 초대 코드를 먼저 보여주려고 **이름 없이 방을 만든 뒤**(서버가 `건강한 친구들`로
지정) 나중에 이름을 정합니다. 그래서 그 사이에 참여한 사람은 방장이 지은 이름을 영영 못 봤습니다.
나중에 누가 방 이름이나 미션 시간을 바꿔도 같은 문제가 생깁니다.

`sync()`가 받아온 그룹 값을 `SET_GROUP_MEMBERS`에서 이름·미션 시간까지 함께 반영합니다.

### 6. 인증은 사진을 반드시 서버로 보내야 합니다

생활습관 미션 인증이 **사진 없이 호출되고 있었습니다.** 화면에는 "AI가 확인해요"라고 떠 있는데
정작 사진은 서버로 가지 않아, 걷기 미션에 채소 사진을 올려도 통과했습니다.

`completeMission(missionId, photo)`는 사진을 multipart로 보냅니다. 서버가 AI로 판정해
맞지 않으면 `MISSION_004`로 거절하므로, **거절됐을 때 완료로 표시하면 안 됩니다.**
`.catch`로 받아 메시지를 화면에 보여주세요.

### 7. 사이클이 끝나면 온보딩부터 다시입니다

"계속하기"는 같은 그룹으로 **새 7일 사이클**을 시작하는 것입니다. 서버가 지난 사이클의
미션·식단·온보딩을 지우므로, 곧바로 그룹 화면으로 보내면 온보딩이 없어 미션이 만들어지지 않습니다.
**온보딩 화면으로 보내야 합니다.**

목표·신체정보는 PRD상 사이클마다 다시 받는 값입니다. 7일 사이에 몸이나 목표가 달라졌을 수 있고,
그래야 AI가 새 기준으로 미션을 만듭니다.

### 8. 미션 개수는 3개가 아닐 수 있습니다

백엔드가 상황에 따라 **1개 / 3개 / 4개**를 내려줍니다
(달성률 90% 이상이면 4개, 3일 연속 실패하면 1개).
3개를 전제로 짜면 화면이 깨집니다.

### 9. 이미지 주소는 `fileUrl()`을 거치세요

서버는 `/api/files/{uuid}` 형태의 상대 경로를 줍니다. 그대로 `<img src>`에 넣으면
프론트 주소를 찾아가서 깨집니다.

### 10. `internalFit`은 화면에 띄우지 마세요

식단 분석 결과의 목표적합도(`good`/`normal`/`bad`)는 **다음 미션 난이도를 정하는 내부 값**입니다.
기획상 사용자에게는 "달성 / 미달성"만 보여줍니다. (애초에 서버가 응답에 담지 않습니다.)

### 11. 이미지가 무거우니 단일 파일 번들로 되돌리지 마세요

`vite-plugin-singlefile`을 쓰면 캐릭터·의상 이미지까지 HTML 하나에 인라인되어
첫 화면이 14MB가 되고, 다 받을 때까지 흰 화면이 유지됩니다.
나눠서 내보내면 처음엔 100KB 정도만 받습니다. 자세한 건 `vite.config.js` 주석 참고.

### 12. 인증 화면에는 "무엇을 찍어야 하는지"가 보여야 합니다

식단 인증(`MealUploadPage`)은 끼니 이름만 알고 미션 제목은 모릅니다. 그래서 예전에는 어떤 미션이든
"아침 사진 업로드"만 떴고, 사용자는 무엇을 찍어야 하는지 알 수 없었습니다.

지금은 `state.missions`에서 **아직 완료되지 않은 첫 번째 식단 미션**을 찾아 제목을 보여줍니다.
서버도 같은 규칙으로 판정 기준을 고르므로(`MissionService.pendingDietMissionTitle`),
이 규칙을 바꾸면 **화면에 보여준 미션과 실제로 판정되는 미션이 어긋납니다.**

### 13. 미션은 하루치가 한 번에 열립니다

예전에는 +3.5h/+7h로 나눠 열려서 "다음 미션은 오후 12:30에 도착해요"가 떴습니다.
PRD 8번은 "설정된 시간에 미션이 동시에 생성된다"이므로, 지금은 세트 전체가 함께 열립니다.
그룹의 미션 시각은 **세트가 도착하는 시각**이지, 미션이 하나씩 열리는 간격이 아닙니다.

`nextUpcomingMission`·`visibleMissions`·`isMissionUnlocked`는 남겨뒀습니다.
서버가 다시 `unlockTime`을 채워 보내면 그대로 동작합니다.

### 14. 탈퇴·나가기는 서버 응답을 기다린 뒤에 화면을 바꾸세요

탈퇴 버튼이 `logout()` + `dispatch`만 하고 있었습니다. 화면에서만 사라지고 DB에는 계정이
그대로 남아, 같은 이메일로 재가입이 막혔습니다.

`deleteAccount()`는 `DELETE /api/auth/me`를 부릅니다. 두 가지를 지켜야 합니다.

- **토큰은 서버 삭제가 끝난 뒤에** 지웁니다. 먼저 지우면 삭제 요청이 401로 거절됩니다.
- **실패하면 화면을 바꾸지 않습니다.** 실패했는데 로그아웃시키면 지워진 줄 알게 됩니다.
